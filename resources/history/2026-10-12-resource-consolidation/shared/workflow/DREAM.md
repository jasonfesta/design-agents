# Dream Mode: refine each direction on its own terms

Version 0.1 · Instructions only · October 12, 2026

During the day, explore quickly and widely. Dream Mode revisits that work, applies Jason's approved standards of taste, resolves unfinished execution, and verifies the result. It can improve hierarchy or composition even when every token is technically correct.

Read [START.md](START.md), [TAXONOMY.md](TAXONOMY.md), the relevant state, and the exact approved baseline. This portable guide follows the definition developed in the separate **Draft design dreaming AGENTS.md** chat: approved category baselines with source links, daytime breadth, overnight refinement, and preservation of distinct ideas.

This file creates no schedule, enrollment, or background agent. A proposed 3 a.m. America/New_York rhythm is context from that discussion, not an active automation. Only run when instructed and within the existing authorized scope.

## Identify exactly what is dreaming

Every target needs a category and a style branch, not just a filename such as “homepage final.” Use this mapping:

```md
- Target ID and exact location:
- Category ID:
- Product scope and user task:
- Style family / treatment:
- Direction ID and current saved/working version:
- Daytime premise and defining choices to preserve:
- Parent category baseline: <immutable ID/version + approval record>
- Branch baseline, if approved: <immutable ID/version + approval record>
- Effective rules: <required rules, defaults, allowed ranges, exceptions>
- Taste packet: <snapshot/revision; applicable confirmed recommendation IDs/revisions>
- Reference IDs and actual attachments needed for visual judgment:
- Dream Mode: off / on
- Included discovery scope: <specific project/folder/page or named designs>
- Exclusions and actively edited areas:
- Editable destinations and existing authorization:
- Verification method and available tools:
```

Resolve inheritance using TAXONOMY.md. A category can share craft standards across several styles. A branch baseline supplies its particular visual rules. If only the category baseline is approved, use it for craft while protecting the candidate brief's visual premise; do not describe the candidate style as approved. Missing category approval permits an assessment or proposed baseline, not autonomous design changes under Dream Mode.

If the category is known but the style mapping is ambiguous, infer a tentative classification for review. Do not repair a target against a guessed visual baseline. Continue with clearly mapped targets and independent checks.

Enrolling a folder can include new work inside that declared boundary. Discover and record its contents at run start. Do not expand discovery to unrelated projects. “Wake this up” disables the named enrollment and stops further edits at the next safe boundary.

## Load the taste recommendations

First run [TASTE.md](TASTE.md) against the design-type/viewport-type/consumer-category/style path. If research is missing, partial, draft, disputed, or inaccessible, tell the user which criteria cannot govern this run. Include coverage, definition/version, and gaps in the taste packet and report. Do not invent taste rules to enable dreaming; skip aesthetic changes depending on missing criteria while continuing covered targets and independent checks. Explicitly scoped approved shared rules can still apply where their mapping is supported.

Nightly dreaming works against our taste recommendations for the target's category and style branch. Receive or assemble a versioned Markdown taste packet containing the approved baseline content and applicable confirmed recommendations: stable IDs, revisions, full wording, scope, reasons, examples, exclusions and recent explicit feedback. Include the design's current premise and actual reference attachments needed for judgment. A pointer to another assistant's memory is not sufficient input.

Keep candidate research interpretations in a separate section. They may inspire a proposal, but cannot become automatic repair rules. Confirmed recommendations guide refinement within the approved baseline; a recorded explicit decision from Jason may update that guidance without another confirmation. A change to a fixed rule must retain the decision as a versioned baseline update or scoped exception.

Pin the effective packet at run start. If governing feedback changes mid-run, refresh the affected comparison and record the new revision. Each meaningful refinement must cite the recommendation or baseline principle it serves. Preserve unresolved conflicts and proceed with independent work. Never apply one branch's recommendation to all categories merely because it is recent.

## The cycle

1. **Resolve the standard.** Load the category/branch's versioned taste packet, pinned baseline versions, relevant evidence, scoped exceptions, current brief and daytime feedback. Record which confirmed recommendation or baseline rule governs each property. A fresh reference or source-site change cannot silently redefine taste.
2. **Capture the starting point.** Save a recoverable snapshot or use the destination's available versioning. Record target revisions, pre-existing edits, candidate identities, and active locks. Keep approved baselines immutable.
3. **Inspect all enrolled targets.** Review source and representative rendered states where available. Record coverage, including inaccessible or unseen designs. A text-only assistant can review specifications, not claim visual inspection.
4. **Diagnose concretely.** Classify each finding as exact drift, unfinished craft, approved variation, identity change, conflicting evidence, or an inspection limitation. State the governing rule/principle and the target-specific weakness.
5. **Refine within scope.** Repair clear drift and exercise design judgment where approved standards permit variation. Improve grouping, hierarchy, typography, spacing, material use, states and responsive behavior while preserving the concept. Fix shared causes when all affected consumers are authorized; otherwise isolate a local change or prepare a proposal.
6. **Verify the change.** Recheck affected states and compare under matching content, viewport and theme. Confirm the direction still meets its identity rules. Fix failures or undo only this run's isolated change. Preserve unrelated edits.
7. **Save and report.** Write a new working/saved version and a concise run record. Keep approved baseline versions unchanged. State what improved, what was preserved, what was verified, and what remains unresolved.

Before each write, check whether another agent or Jason has changed the target or baseline since inspection. Refresh the comparison if so. Stop editing targets that have been woken up. Reuse existing authorization for routine refinements; do not introduce a per-adjustment approval loop.

## What good judgment looks like

| Situation | Action |
| --- | --- |
| A caption uses a value outside the approved type scale | Restore the intended role; verify wrapping and information hierarchy. |
| All values are valid, but condition details are visually lost | Rework grouping/emphasis within the branch's rules and verify the task remains clear. |
| The poster direction intentionally has stronger display type than the catalogue direction | Preserve both premises and improve each one's readability. |
| A locked image treatment conflicts with a new inspiration reference | Keep the lock. Offer a separate candidate; do not rewrite the baseline. |
| A category-wide required rule conflicts with a branch default | Apply the required rule where its mapping is clear; surface any unresolved conflict. |
| The approved old pattern creates an inaccessible or broken interaction | Preserve functionality and accessibility, report the baseline conflict, and propose a correction. |
| No specific weakness remains and there is no new input | Make no change. Do not oscillate between equally valid arrangements. |

Do not select a winner, discard alternatives, change product flow, replace the visual premise, or convert an experiment into a personal convention unless Jason has authorized that scope. Ordinary craft improvements within approved standards do not require an exact numeric instruction for every decision.

## Morning record

```md
# Dream report — <run ID/date>
- Categories, scopes, branches, target revisions and baseline versions:
- Taste packet revision; applicable confirmed recommendation IDs/revisions:
- Discovery boundary and coverage: <inspected / discovered; inaccessible items>
- Preserved: <each direction's defining idea and intentional exceptions>
- Repaired: <target, mismatch, governing exact rule, before → after>
- Refined: <target, weakness, recommendation ID or baseline principle/evidence, change and reason>
- Verification: <actual checks and evidence; not-run or unseen states>
- New saved versions and recoverable starting snapshots:
- Proposed baseline changes: <separate from working refinements>
- Unresolved decisions or conflicts; remaining work and continuation point:
```

Use outcome labels: **meets the standard**, **improved and verified**, **changed but unverified**, **needs a decision**, or **not inspected**. Preserve rejection reasons so later runs do not repeat the same unwanted change without new evidence.

In a Markdown-only environment, produce revised specifications and exact change instructions, explicitly labeled **not applied to a rendered design**. With authorized editing/execution tools, carry the changes through and report the evidence. Neither situation authorizes deployment, publication, or a new automation by itself.
